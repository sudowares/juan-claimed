01

System overview

One request path from browser to database, plus the three external services the backend calls out to.
primary request path secondary / metadata-only

The frontend never talks to Postgres, eGovPH, or Blob storage directly except for the upload itself — every other read or write is mediated by the backend's service layer, and the eligibility engine and the eGov client are the two services with an external dependency (the database and the eGovPH platform, respectively). Attachment bytes go client → Blob directly; only the resulting URL round-trips through the backend.

02

eGovPH sign-in sequence

One exchange code becomes this backend's own JWT — and seeds the citizen's first answers along the way.
request response

The token the frontend ends up with (step 9) is this backend's own JWT, signed with JWT_SECRET — eGov's access_token from step 4 is single-use and never leaves the backend. Steps 7–8 are what make eGovPH sign-in more than authentication: known profile fields (date of birth, residence, name) are written straight into the citizen's answers on first login, so the eligibility quiz never re-asks something eGov already told us.

03

Eligibility engine — leaf evaluation

The one piece of logic where "no answer yet" and "answered, left blank" have to be told apart.

Two things make a field PENDING instead of a hard NOT_ELIGIBLE even without a usable answer: never having been asked, or having been asked and left blank — both keep resurfacing in "Answer More" unless another, already-decided condition has definitively hidden that field. The one carve-out is IS_EMPTY/IS_NOT_EMPTY: for those operators a null value is the answer being tested, so it's compared for real instead of deferred. Applies identically to a signed-in citizen and to a guest's in-browser answers.

04

eGov API integration points

One client, three eGovPH products, each wired to a live route.

All three calls fail closed and silently when unconfigured — a blank EGOV_MESSAGE_BASE_URL skips SMS per user with a log line rather than failing the benefit publish that triggered it.

05

Data model

A benefit is a rule tree over reusable fields; a citizen is a set of answers to those same fields.

Fields are the reusable layer: the same DimField (e.g. "Number of Employees") can be referenced by many benefits' rule trees, can anchor to another field so it only renders once its parent is answered, and can attach to a DimFieldHierarchy for tree-shaped answers like PSGC location or a business-sector taxonomy. Simplified from the full schema — supporting dimension tables (countries, schools, option lists) are omitted.

06

Deployment pipeline

A push builds once and lands on the VPS as a pull, never a rebuild on the server.

The two VPS compose files only ever pull — no build:, no bind mount, no git checkout on the server. Each push tags images two ways: a floating latest/staging tag plus an immutable <branch>-<timestamp>-<sha> tag, so rolling back is re-pointing the compose file at an older tag, not re-building. Postgres and Prisma Studio have no public port in either stack — only Nginx is reachable from outside.
